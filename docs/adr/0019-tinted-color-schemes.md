# ADR-0019: Community color schemes for the window and the terminal

- Status: Accepted (2026-10-29); the mode's reach in decision 2 superseded by [ADR-0026](0026-the-theme-mode-filters-the-color-schemes.md)
- Date: 2026-10-29

## Context

The maintainer asked for the whole app, the window and the terminal, to be rethemable with every community theme. The tinted-theming project offers 498 schemes imported from [tinted-theming/schemes](https://github.com/tinted-theming/schemes) (MIT, each scheme's author credited). Web themes keep only CSS tokens derived from them, but a terminal needs the 16 ANSI colors. So we import the schemes themselves, at a pinned commit (`3ac91137e879`), into our own catalog.

Our own light and dark themes stay the default identity ([ADR-0010](0010-original-work-only.md)). Schemes are something the user chooses.

## Decision

1. **The catalog** is generated by `cargo xtask themes <checkout>` into `annulus-config/src/schemes/catalog.rs`, with the MIT license and every scheme's author in `LICENSE.txt` beside it. Both are committed, so builds never need the network. Each scheme's 24 base colors are stored as-is. base16 schemes are filled to 24 with the base24 fallback. Import is defensive: the checkout is untrusted (it reads only flat YAML, requires `#rrggbb` colors and slug file names, and cleans names), base24 wins when a scheme exists in both systems, and a scheme whose text and background are indistinguishable is dropped.
2. **Two separate choices:** Settings → Appearance → *Color scheme* recolors the window (`app_scheme`, `None` = ours). Settings → Terminal → *Colors* lists our built-in terminal themes and then every scheme they do not already name (`terminal_theme`). A scheme is light or dark by itself: the System/Light/Dark mode applies only to our own theme.
3. **Derived, not hand-tuned.** `Scheme::palette()` maps a scheme onto our design tokens:
   - the panels are the scheme's background (`base00`), and the window sits one contrast step deeper;
   - the raised, hover and border colors step toward the text;
   - the accent is `base0D`, and the status colors are `base08`, `base0A` and `base0B`.

   `Scheme::terminal()` uses the base24 styling guide's ANSI table (black is `base00`, bright black is `base03`, the brights are `base12`–`base17`, the selection is `base02`). A color that falls short of our contrast rules is moved toward white (dark schemes) or black (light schemes), only as far as it must go. Tests hold every scheme to the same WCAG AA bar as our own themes (`every_scheme_meets_wcag_aa`, `every_scheme_keeps_terminal_text_readable`).
4. **The toolkit theme** is built from any token set (`Theme::from_palette`). Our light theme keeps its white cards because its tokens say white, not because the toolkit forces it.

## Consequences

- The binary grows by about 36 KB of colors. Each scheme's tokens are worked out once and cached.
- A scheme can look a little different from its author's version where we raised contrast. Accessibility wins.
- Updating the schemes is a regenerate-and-commit step. The dropped ones are printed.
- Our own themes remain the only defaults, and no other product's palette is involved.

## Alternatives considered

- **Reuse a web theme's CSS tokens.** They have no ANSI colors and are tied to web token names.
- **One choice for both window and terminal** (a common model). The maintainer chose separate pickers.
- **Follow the OS by switching a scheme's light/dark counterpart.** The maintainer chose fixed schemes.
